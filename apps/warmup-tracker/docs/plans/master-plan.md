# Master Plan: warmup-tracker Service Improvements

## Overview

This document serves as the central coordination plan for all improvements to the `warmup-tracker` service. It links to individual sub-plans and establishes the execution order, dependencies, and success criteria for the full improvement initiative.

## Service Summary

The `warmup-tracker` service is a NestJS Cloud Function that:

- Exposes a `POST /notify` endpoint
- Receives warmup event data from email warmup workflows
- Queries PostgreSQL (`warmup_users` table via TypeORM) for user context
- Builds Slack Block Kit messages with Gmail deep-link buttons
- Sends notifications via `@slack/web-api`

### Key Components

| Component | File | Responsibility |
|---|---|---|
| AppController | `src/app.controller.ts` | HTTP routing, `POST /notify` |
| AppService | `src/app.service.ts` | Core business logic: `notify()`, `parsePayload()`, `removePlaceholders()` |
| SlackService | `src/slack/slack.service.ts` | Slack SDK wrapper: `sendMessage()` |
| WarmupUser entity | `src/entities/warmup-user.entity.ts` | TypeORM entity for `warmup_users` table |

## Improvement Areas and Sub-Plans

### 1. Test Coverage Plan

**File**: `docs/plans/test-coverage-plan.md`

**Goal**: Increase test coverage from < 10% to >= 80% across all service files.

**Scope**:
- Unit tests for `AppService` (all three methods)
- Unit tests for `SlackService`
- Integration/unit tests for `AppController`
- Entity validation tests for `WarmupUser`

**Priority**: High — without adequate tests, all other changes carry risk of regression.

**Estimated Effort**: 3-5 days

---

### 2. Dependency Upgrade Plan

**File**: `docs/plans/dependency-upgrade-plan.md`

**Goal**: Audit and upgrade all dependencies to current stable versions compatible with the existing tech stack.

**Scope**:
- NestJS ecosystem packages
- TypeORM and database drivers
- `@slack/web-api`
- Dev dependencies (ESLint, Jest, TypeScript)
- Security audit via `npm audit` / `pnpm audit`

**Priority**: Medium — should be done after test coverage is in place to catch regressions.

**Estimated Effort**: 1-2 days

---

### 3. pnpm Migration Plan

**File**: `docs/plans/pnpm-migration-plan.md`

**Goal**: Resolve the `npm` vs `pnpm` inconsistency by standardizing on `pnpm` throughout.

**Scope**:
- Update `package.json` scripts to use `pnpm`
- Update `Dockerfile` to be consistent
- Add `pnpm-lock.yaml`, remove `package-lock.json`
- Update CI/CD pipeline references if applicable
- Add Volta `pnpm` configuration

**Priority**: Medium — depends on test coverage being in place to validate the build after migration.

**Estimated Effort**: 0.5-1 day

---

### 4. Final Verification Plan

**File**: `docs/plans/final-verification-plan.md`

**Goal**: Validate all improvements are correctly applied and the service is production-ready.

**Scope**:
- Run full test suite and verify coverage thresholds
- Build Docker image and verify size reduction
- Validate `pnpm` lockfile consistency
- Smoke test the `POST /notify` endpoint
- Security audit pass

**Priority**: High — must be completed last, after all other plans.

**Estimated Effort**: 0.5 day

---

## Execution Order

The sub-plans must be executed in the following order due to dependencies between them:

```
1. Test Coverage Plan
        |
        v
2. Dependency Upgrade Plan
        |
        v
3. pnpm Migration Plan
        |
        v
4. Final Verification Plan
```

**Rationale**:

- Tests must exist before upgrading dependencies so regressions are caught immediately.
- Dependencies should be upgraded before migrating the package manager so that the lockfile generated by `pnpm` reflects the final dependency set.
- Final verification must run last to confirm the cumulative state of all changes.

## Success Criteria (Master)

The improvement initiative is complete when ALL of the following are true:

- [ ] Overall line coverage >= 80% (enforced in Jest config)
- [ ] Overall branch coverage >= 75%
- [ ] All tests pass (`pnpm test`)
- [ ] `pnpm audit` reports zero high or critical vulnerabilities
- [ ] `package.json` scripts use `pnpm` exclusively
- [ ] `Dockerfile` uses `pnpm` exclusively and uses multi-stage build
- [ ] `package-lock.json` is absent; `pnpm-lock.yaml` is present and committed
- [ ] Docker image builds successfully
- [ ] `POST /notify` endpoint returns expected responses under test conditions
- [ ] No ESLint errors or warnings

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Breaking API changes in `@slack/web-api` upgrade | Medium | High | Pin to minor version, review changelog, test `SlackService` thoroughly |
| TypeORM migration breaking entity schema | Low | High | Keep entity unchanged unless schema migration is explicitly planned |
| pnpm lockfile conflicts in CI/CD | Medium | Medium | Update CI pipeline scripts in same PR as pnpm migration |
| Test mocks not reflecting real Slack API behavior | Medium | Medium | Use Slack API type definitions for mock shapes |
| Docker image fails to build after multi-stage refactor | Low | Medium | Test build locally before merging |
