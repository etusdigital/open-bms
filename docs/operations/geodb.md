# GeoIP Enrichment — Setup & Operations

The BMS pipeline can enrich tracking events with country / region / city
fields resolved from the visitor IP. This document is the single reference
for all tiers, the configuration flow from wizard to runtime, the refresh
pipeline, and operational runbooks.

---

## Tiers

| Tier       | Source                      | Cost            | Granularity       | Refresh cadence |
| ---------- | --------------------------- | --------------- | ----------------- | --------------- |
| `disabled` | —                           | free            | none              | n/a             |
| `lite`     | DB-IP Lite City (CC-BY 4.0) | free            | country + city    | monthly (1st)   |
| `full`     | DB-IP subscriber API        | paid (DB-IP)    | full + ASN traits | monthly (1st)   |
| `maxmind`  | MaxMind GeoLite2 City       | free (license)  | country + city    | weekly          |
| `api`      | ip-api.com Pro / ipinfo.io  | paid (provider) | varies            | live HTTP       |

Default tier is `lite` — works out of the box with no signup. Attribution is
required: surface "IP geolocation by [DB-IP.com](https://db-ip.com)" wherever
geo fields are displayed.

Tiers `api` and `disabled` do not download or use a local MMDB. The refresh
sidecar exits immediately for these tiers without doing any work.

## How configuration reaches the runtime

There is a deliberate separation between **where settings are stored** (the
wizard / admin UI → Postgres) and **how the runtime reads them** (env vars
sourced from a shared file). Understanding this bridge is key to operating
GeoIP correctly.

### The canonical config file: `/data/config/geoip.env`

`msgops-api` writes this file whenever:

- The GeoIP step is submitted in the setup wizard (`POST /api/setup/geoip`).
- A super-admin saves the GeoIP settings via the admin UI (`PUT /api/admin/geoip/settings`).
- `msgops-api` starts and the file is missing but `system_config.geoip_settings` has data
  (bootstrap — covers first boot after upgrading to this version, or a volume wipe).

The file contains plain `KEY=VALUE` lines and is the source of truth for the
runtime. Example for DB-IP Full:

```env
# Generated by BMS. Do not edit manually — overwritten on each save.

GEO_TIER=full
DBIP_API_KEY=your-api-key
```

### Who reads it

| Consumer              | When                          | How                                                               |
| --------------------- | ----------------------------- | ----------------------------------------------------------------- |
| `geolocation-refresh` | Start of every download cycle | `set -a; . geoip.env; set +a` in bash                             |
| `apps/geolocation`    | Container start               | `loadWizardConfig()` in `src/main.ts` before `NestFactory.create` |

Because `apps/geolocation` reads the file at boot, a tier or credential
change takes effect on the next container restart — no code reload needed.
The `geolocation-refresh` sidecar re-reads the file at each download cycle,
so a credential rotation is picked up without a container restart.

### Priority order (highest first)

1. `/data/config/geoip.env` — wizard / admin save (always wins)
2. `apps/geolocation/.env` — fallback for fresh installs and local dev
3. Compose `environment:` block — infrastructure-only (`GEO_MMDB_DIR`, `BMS_CONFIG_DIR`)

> ⚠️ Never add `GEO_TIER` or credential vars to the `environment:` block in
> `docker-compose.yml`. Compose `environment:` overrides `env_file:` by
> precedence, which would silently shadow both the `.env` file and the wizard
> config file.

### Volume and permissions

The file lives in the `bms-config` named Docker volume mounted at `/data/config`:

| Service               | Mount                     | Access |
| --------------------- | ------------------------- | ------ |
| `msgops-api`          | `bms-config:/data/config` | rw     |
| `geolocation`         | `bms-config:/data/config` | ro     |
| `geolocation-refresh` | `bms-config:/data/config` | ro     |

`msgops-api` runs as UID 1001 (non-root). A one-shot `bms-config-init`
service runs before `msgops-api` on every `docker compose up` and sets
`chown 1001:1001 /data/config` on the volume, so no manual `chmod` is ever
needed.

To inspect the file from outside the containers:

```bash
# via a one-off ephemeral container (no shell needed in running containers)
docker run --rm -v <project>_bms-config:/data/config alpine cat /data/config/geoip.env

# find the exact volume name
docker volume ls | grep bms-config

# or exec directly into msgops-api
docker exec msgops-api cat /data/config/geoip.env
docker exec msgops-api ls -la /data/config/
```

## Changing GeoIP settings

### During initial setup (wizard)

The setup wizard (Step 4) presents three choices: Disabled / Lite / Advanced.
Submitting the step calls `POST /api/setup/geoip`, which persists the
selection in `system_config.geoip_settings` and immediately writes
`/data/config/geoip.env`. The sidecar picks up the new tier on its next
download cycle; `apps/geolocation` picks it up on the next container start.

### After setup (admin settings UI)

Super-admins can change the GeoIP configuration at any time via
**Settings → GeoIP** in the frontend. This calls `PUT /api/admin/geoip/settings`
which follows the same path: saves to DB → writes config file. Credentials
are never displayed in full — the response returns a masked preview
(`abc***xyz`). Leaving a credential field blank on save keeps the existing
value in the DB (the backend merges). Switching providers clears the
previous provider's credentials.

### Applying the change

Writing the config file is not enough on its own to change the active tier:

1. **`apps/geolocation`** reads the file at boot → restart required:
   ```bash
   docker compose up -d --force-recreate geolocation
   ```
2. **`geolocation-refresh`** reads the file at the start of each download
   cycle → it will pick up the new tier automatically on the next daily run.
   To download with the new tier immediately:
   ```bash
   make geo-refresh-force
   # or directly:
   docker exec geolocation-refresh bash /workspace/scripts/download-geodb.sh
   ```

## Refresh pipeline

The `geolocation-refresh` sidecar runs `scripts/download-geodb.sh`:

- **On container start** — immediately, so a `--force-recreate` always
  fetches a current file without waiting for the next scheduled run.
- **Daily at 06:00 UTC** — via `crond` inside the container.

### What the script does

1. Sources `/data/config/geoip.env` (wizard/admin config) then
   `apps/geolocation/.env` (fallback). This ensures the latest tier and
   credentials are always used, even after an admin change without a container
   restart.
2. Exits cleanly (`exit 0`) for `api` and `disabled` tiers — no MMDB to download.
3. Downloads to `${DEST}.tmp` — never touches the live MMDB until
   validation passes.
4. Decompresses (skipped for `maxmind` — `geoipupdate` writes `.mmdb` directly).
5. Validates: file size bounds + IP fixture assertions
   (`mmdb-fixtures-lite.json` for `lite`/`maxmind`, `mmdb-fixtures.json` for `full`).
6. **MD5 idempotency check** — compares the staged file against the current
   MMDB. If they match, exits without swapping. This makes daily runs on
   non-release days cost only one download + compare (no swap, no watcher
   reload, no unnecessary service activity).
7. Atomic `mv` to `${DEST}` + `touch` to bump mtime.
8. `apps/geolocation` watches the directory via `chokidar` and reloads the
   in-memory `MMDBReader` automatically — no restart needed.

### Why daily instead of monthly

DB-IP publishes on the 1st of each month. Running daily means:

- **Automatic retry** — if the 1st fails (provider outage, bad file, network
  blip), the 2nd picks it up automatically.
- **Provider agnostic** — MaxMind (weekly), DB-IP Full (monthly), and any
  future provider all benefit from the same cadence without per-provider
  scheduling logic.
- **Near-zero cost on idle days** — the MD5 check exits early when nothing
  changed, so bandwidth and CPU are only consumed when a new file is actually
  available.

## Manual refresh commands

### `make geo-refresh` — host-side run (no docker, no cron)

Executes `scripts/download-geodb.sh` directly in the caller's shell. Loads
`apps/geolocation/.env` automatically (same source as the compose `env_file:`).
Useful in dev or to bootstrap `data/geo/` before the first `docker compose up`.

```bash
make geo-refresh                              # loads apps/geolocation/.env
pnpm geo:refresh                              # equivalent via pnpm
GEO_TIER=full bash scripts/download-geodb.sh  # one-shot override (bypasses .env)
```

> Note: `make geo-refresh` does **not** read `/data/config/geoip.env` (the
> named volume is not accessible from the host). It relies on `apps/geolocation/.env`.
> For a one-off override, pass vars inline when calling the script directly.

### `make geo-refresh-force` — trigger the sidecar now

Runs `download-geodb.sh` inside the live `geolocation-refresh` container using
`docker compose exec`. The script runs with the same image, volumes, and
environment the cron path uses — including reading `/data/config/geoip.env` —
so it exercises the exact production code path on demand.

```bash
make geo-refresh-force
pnpm geo:refresh:force   # equivalent via pnpm
```

If the sidecar isn't running, the target falls back to
`docker compose up -d --force-recreate geolocation-refresh`, which triggers
an immediate download on container start.

### When to use which

| Situation                                               | Command                  |
| ------------------------------------------------------- | ------------------------ |
| Local dev, no docker stack running                      | `make geo-refresh`       |
| Bootstrap `data/geo/` before first `docker compose up`  | `make geo-refresh`       |
| Sidecar running, need fresh download now                | `make geo-refresh-force` |
| Changed tier via admin UI, want to apply immediately    | `make geo-refresh-force` |
| One-off download from a dev machine against a paid tier | `make geo-refresh`       |

## Switching tiers (operator runbook)

The recommended path for all tier changes is the **admin settings UI**
(Settings → GeoIP), which writes `geoip.env` automatically. The runbooks
below describe the container steps required after saving.

### Any tier change

```bash
# 1. Use the admin UI or API to save the new tier and credentials.
#    This writes /data/config/geoip.env automatically.

# Via API (super-admin token required):
curl -X PUT https://app.example.com/api/admin/geoip/settings \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"mode":"advanced","provider":"dbip-full","apiKey":"..."}'

# 2. Recreate geolocation so it reads the updated geoip.env on boot.
docker compose up -d --force-recreate geolocation

# 3. Force an immediate download with the new tier (optional — the daily
#    cron would pick it up at 06:00 UTC otherwise).
make geo-refresh-force
```

### MaxMind

The MaxMind EULA forbids redistributing the database in a public image. The
sidecar relies on the official `geoipupdate` binary, which must be present in
the `geolocation-refresh` image. For the `node:20-alpine` base, install it
with `apk add --no-cache geoipupdate` in a custom Dockerfile or add it to the
sidecar entrypoint's `apk add` line.

### Disabling enrichment

`GEO_ENRICHMENT_ENABLED` is consumed by `apps/event-process` and must live in
that app's env file:

```bash
echo "GEO_ENRICHMENT_ENABLED=false" >> apps/event-process/.env
docker compose restart event-process
```

Setting `mode=disabled` in the wizard/admin UI writes `GEO_TIER=disabled` to
`geoip.env`, which stops the sidecar from downloading MMDBs, but does not stop
`apps/event-process` from calling the gRPC service. Use `GEO_ENRICHMENT_ENABLED`
to cut enrichment entirely at the pipeline level.

## Admin API

All endpoints require a super-admin JWT (`Authorization: Bearer <token>`).

### `GET /api/admin/geoip/status`

Aggregated runtime view: wizard settings + live gRPC state + Redis cache stats.

```bash
curl -H "Authorization: Bearer ${TOKEN}" \
     https://app.example.com/api/admin/geoip/status
```

```json
{
  "settings": { "mode": "lite" },
  "runtime": {
    "tier": "lite",
    "mmdbPath": "/data/geo/dbip-city-lite.mmdb",
    "mmdbSizeBytes": 134217728,
    "mmdbMtimeMs": 1714867200000,
    "lastReloadAt": "2026-05-01T03:00:00.000Z",
    "lookupCount": 4821933,
    "ready": true
  },
  "cache": { "enabled": true, "keyCount": 41892 }
}
```

`runtime: null` — gRPC service unreachable (container down or network issue).
`settings: null` — wizard step never ran.

Use the delta between `settings.mode` and `runtime.tier` to detect when a
config change has been saved but not yet applied (container not recreated).

### `GET /api/admin/geoip/settings`

Returns the persisted settings with credentials masked. Safe to display in a UI.

```json
{
  "mode": "advanced",
  "provider": "dbip-full",
  "apiKeyMasked": "abc***xyz"
}
```

### `PUT /api/admin/geoip/settings`

Saves a new configuration. Credentials are optional: omitting a credential
field keeps the existing value for the same provider. Switching providers
drops the previous provider's credentials — the new ones must be supplied.

```bash
curl -X PUT https://app.example.com/api/admin/geoip/settings \
  -H 'Authorization: Bearer ${TOKEN}' \
  -H 'Content-Type: application/json' \
  -d '{"mode":"advanced","provider":"maxmind","accountId":"123456","licenseKey":"..."}'
```

Writes `geoip.env` immediately. Container restarts are still required to apply
the new tier to the running services (see "Applying the change" above).

## Validation guard rails

`scripts/validate-mmdb.ts` runs before every swap. It rejects files outside
the configured size range and asserts a fixed set of stable IP fixtures
resolve correctly (`scripts/mmdb-fixtures-lite.json` for `lite`/`maxmind`,
`scripts/mmdb-fixtures.json` for `full`). A corrupted or truncated download
does not overwrite the live MMDB — the previous file keeps serving lookups
and the sidecar exits non-zero so the failure shows up in container logs.

Fixture assertions for the Lite tier use `region_name_contains` (subdivision
name substring) instead of `region_iso` because DB-IP Lite does not include
ISO subdivision codes.

To skip validation (e.g. bootstrapping with an externally built MMDB), set
`GEO_REFRESH_SKIP_VALIDATION=1` in the compose environment. Size bounds still
apply even with validation skipped.

## Data flow — MMDB vs Redis

The MMDB file and Redis serve completely different purposes and never interact
directly. Understanding the separation is key to reasoning about the system.

```
scripts/download-geodb.sh
        │
        ▼ atomic mv (validated)
  data/geo/dbip-city-lite.mmdb   ← binary file on disk (~125 MB)
        │
        ▼ loaded into memory at container start (chokidar reloads on mtime change)
  apps/geolocation               ← gRPC microservice; mmdb-reader resolves IPs in-process
        │
        ▼ gRPC call per unique IP (cache miss only)
  CachedGeoProvider              ← in packages/geo; wraps any GeoProvider
        │
        ├─ GETEX geo:lookup:v1:<ip> ──► Redis (cache hit → return immediately)
        │
        └─ cache miss → gRPC → geolocation → reads MMDB from memory
                                           └─ SETEX geo:lookup:v1:<ip> → Redis
                                                          │
                                                          ▼
                                               country / region / city / traits
                                                          │
                              ┌───────────────────────────┼──────────────────────┐
                              ▼                           ▼                      ▼
                    ClickHouse columns          Redis stat counters        bot-detector.ts
                 (country, region, city)    (country_open_US +1, etc.)   (traits → is_bot,
                  events_logs_v2                                          bot_classification)
```

### Key points

**The MMDB is never written to Redis.** The download script writes a binary
file to disk. `apps/geolocation` loads the entire file into memory on start
(and reloads when `chokidar` detects a mtime change). Redis only ever stores
the result of individual IP lookups — a small JSON payload per IP, populated
on demand as events arrive.

**Redis warms up organically.** There is no bulk pre-load. The first lookup
for each IP is a cache miss (hits gRPC → MMDB in memory), subsequent lookups
within the TTL window are cache hits (Redis only, no gRPC call). In practice,
mail scanner IPs from Gmail, Outlook, and Yahoo dominate open events and
represent a very small pool of unique addresses — cache hit rate reaches 95 %+
within minutes of the first traffic.

**Two separate Redis key spaces:**

| Key pattern                      | Written by                     | Purpose                                                          |
| -------------------------------- | ------------------------------ | ---------------------------------------------------------------- |
| `geo:lookup:v1:<ip>`             | `CachedGeoProvider`            | Lookup result cache — avoids repeated gRPC calls for the same IP |
| `country_<event>_<country>` etc. | `EventsService` (pre-existing) | Campaign stat counters consumed by `msgops-api` analytics        |

The stat counters (`HINCRBY`) are pipelined with other event counters and
predate the GeoIP cache work — they are written for every enriched event
regardless of whether the result came from cache or gRPC.

**Disabling the cache** (`GEO_CACHE_ENABLED=false`) removes the Redis lookup
layer entirely — every event calls gRPC directly. The stat counters are
unaffected (they run after enrichment, regardless of how the lookup was served).

## Caching

Lookups are cached per-IP in Redis under the `geo:lookup:v1:` prefix.

| Setting                      | Default | Effect                            |
| ---------------------------- | ------- | --------------------------------- |
| `GEO_CACHE_ENABLED`          | `true`  | Set `false` to disable entirely   |
| `GEO_CACHE_TTL_SECONDS`      | `86400` | TTL for successful lookups (24h)  |
| `GEO_CACHE_NULL_TTL_SECONDS` | `3600`  | TTL for failed/empty lookups (1h) |

To invalidate all cached entries, bump the version suffix in the key prefix.
Edit `keyPrefix` in `packages/geo/src/providers/cached-geo.provider.ts` from
`geo:lookup:v1:` to `geo:lookup:v2:` (or any new value). Old keys expire
naturally after their TTL.

## Troubleshooting

**`apps/geolocation` reports `ready: false`**
MMDB is missing or unreadable at `${GEO_MMDB_DIR}/<tier-filename>`. Check
the sidecar logs (`docker logs geolocation-refresh`) and verify the tier
mapping — `ls $(docker exec geolocation env | grep GEO_MMDB_DIR | cut -d= -f2)`
shows what's actually on disk.

**Events have empty geo fields but `lookupCount` is growing**
The `CachedGeoProvider` may be serving stale `null` entries from a previous
failed lookup. Either wait for `GEO_CACHE_NULL_TTL_SECONDS` to expire or
bump the cache key prefix to force a fresh lookup for all IPs.

**Validator rejects every download**
The fixture assertions may be out of date for a newly-released MMDB version
(providers occasionally change ISP/city assignments for well-known IPs).
Probe the new file with `pnpm tsx scripts/validate-mmdb.ts <path> <fixtures>`
and update the `expect` blocks in `scripts/mmdb-fixtures-lite.json` if the
new values are authoritative.

**Config change not reflected in the running geolocation service**
`apps/geolocation` reads `geoip.env` once at boot. Saving via the admin UI
writes the file, but the service needs a restart to pick it up:

```bash
docker compose up -d --force-recreate geolocation
```

**Sidecar downloading the wrong tier despite correct config**
Check which file is actually in the volume:

```bash
docker exec geolocation-refresh ls -lh /data/geo/
```

If the wrong file is there, the sidecar may have run before the config file
was written (e.g. on first start before the wizard). Run `make geo-refresh-force`
after confirming `geoip.env` has the correct content.

## Common pitfalls

1. **`/data/config/geoip.env` wins over everything else.** The wizard or admin
   UI writes this file, and it is sourced first — before `apps/geolocation/.env`
   and before shell environment variables. If a setting looks wrong despite
   editing `.env`, check whether `geoip.env` is overriding it:
   `docker exec msgops-api cat /data/config/geoip.env`

2. **Don't put tier/credential vars in the root `.env`.** Compose only
   interpolates root `.env` into `${VAR}` placeholders within the compose
   file itself. Service environments come from per-app `env_file:` blocks.
   `GEO_TIER=full` in root `.env` is silently ignored.

3. **Don't add `GEO_TIER` or credential vars to the `environment:` block in
   `docker-compose.yml`.** Compose `environment:` overrides `env_file:`, so
   adding them there silently shadows both `apps/geolocation/.env` and the
   wizard config file. Only infrastructure vars (`GEO_MMDB_DIR`,
   `BMS_CONFIG_DIR`, `PORT`) belong in `environment:`.

4. **`apps/geolocation` reads `geoip.env` once, at boot.** A config change
   via the admin UI writes the file immediately, but the service doesn't
   re-read it — a container restart is required. The MMDB file-watcher is
   separate: it reloads the database when the file on disk changes, but it
   does not re-read env vars.

5. **`GEO_TIER` drives both the data source and the filename.** You cannot
   set them independently. Tier `lite` always produces `dbip-city-lite.mmdb`,
   `full` always produces `dbip-city-full.mmdb`, `maxmind` always produces
   `geolite2-city.mmdb`. Files for different tiers coexist in `GEO_MMDB_DIR`
   without overwriting each other.

6. **`make geo-refresh` (host-side) does not read `geoip.env` from the named
   volume.** Named volumes are managed by Docker and not accessible as plain
   host paths. Host-side runs load `apps/geolocation/.env` only. Use
   `make geo-refresh-force` (runs inside the container) when you need the
   wizard/admin settings to apply.

## Where geolocation is used

### `apps/event-process` — the primary consumer

`apps/event-process` is the only app that calls `geoProvider.lookup(ip)`. The
lookup is gated by `GEO_ENRICHMENT_ENABLED=true` in `apps/event-process/.env`;
when that flag is absent or `false`, the method returns `{}` immediately
regardless of the configured provider.

The lookup is centralised in `EventsService.getGeoIpInfo()` (
`src/events/services/events.service.ts:42-59`). All event sub-services call
that shared method:

| Sub-service     | File                            | Events enriched             |
| --------------- | ------------------------------- | --------------------------- |
| SendGrid        | `sendgrid.service.ts:170`       | `open`, `click`             |
| Push            | `push.service.ts:31`            | `click`                     |
| Twilio          | `twilio.service.ts:24`          | `click`                     |
| Internal events | `internal-events.service.ts:94` | all events that carry an IP |
| Custom events   | `custom-events.service.ts:92`   | all events that carry an IP |

### What happens to the data

```
lookup(ip)
 ├─ country / region / city ──► ClickHouse: BMS.events_logs_v2 columns
 │                         ──► Redis counters: country_<event>_<country>, etc.
 └─ traits (ASN, userType) ──► bot-detector.ts → is_bot / bot_classification
                           ──► written to the `properties` JSON column in ClickHouse
                           ──► NOT written as standalone columns (no schema column)
```

`traits` are never persisted directly — they are consumed by
`apps/event-process/src/utils/bot-detector.ts` to classify mail scanners
(Gmail, Outlook, Yahoo), automation scripts, and datacenter IPs. The resulting
signals (`is_bot`, `is_datacenter`, `bot_classification`, `asn`, `asn_org`,
`user_type`) land in the `properties` JSON column.

### `apps/msgops-api` — admin diagnostics only

`apps/msgops-api` imports `@bms/geo` but does **not** call `geoProvider.lookup()`.
It registers a private gRPC client (`GEO_GRPC_CLIENT_ADMIN` token in
`src/modules/admin-geoip/admin-geoip.module.ts`) solely to call `GetStatus`
on the geolocation microservice for the admin status endpoint.

## Where geolocation could be used

### `apps/tracker` — not integrated yet

`apps/tracker` is the pixel/link-click tracker that receives raw HTTP hits
before they reach `apps/event-process`. It currently does **not** import
`@bms/geo` and does not enrich events with geo data at capture time.

Integrating geo enrichment here would allow:

- Storing the visitor country/city on the first HTTP request, before the event
  enters the async processing queue — reducing latency between click and geo-enriched
  record in ClickHouse.
- Filtering or rate-limiting by country at the tracker layer (e.g. block known
  bot-heavy regions before they generate queue load).

This integration is listed as a follow-up in the GeoIP architecture ADR
(`docs/plans/2026-04-30-adr-geo-grpc-architecture.md`). The recommended path
is to add `GeoModule.register()` to `apps/tracker` with `GEO_PROVIDER=local`
and call `geoProvider.lookup(ip)` inside the click/open handler, before
publishing to the event queue — keeping the same `GEO_ENRICHMENT_ENABLED` flag
as the gate.

### Campaign analytics — contact-level geo

Contact records in `apps/msgops-api` already carry `city`, `region`, and
`country` columns (populated during import, not from enrichment). These are
separate from event-level geo — they represent where the contact was when their
profile was created, not where they opened an email.

A future enrichment pass could cross-reference event geo data against contact
records to keep contact location fields up to date as events arrive, without
requiring a re-import.
